## 二、风险清单

### P0-1：用户可控 URL 造成 SSRF

- 位置：`artifacts/api-server/src/routes/upload.ts` 的 `fetchPageText()`（约 177–188 行）。
- 现状：服务端直接 `fetch(url)`，会跟随重定向；没有限制协议、目标端口、私网/回环/链路本地地址，也没有在 DNS 解析后复核地址。
- 影响：登录用户可能借此访问云元数据、数据库管理端口或其他仅内网可见服务，并把响应内容送入后续解析流程。
- 修复：只允许 `http/https`；解析 DNS 并拒绝私网、回环、链路本地、保留地址；每次重定向重新校验；限制重定向次数、响应大小和 Content-Type；生产环境增加出站网络白名单。

### P0-2：上传、并发任务和 AI 调用可造成内存/费用型拒绝服务

- 位置：`artifacts/api-server/src/routes/upload.ts`（PDF 使用 `memoryStorage`，单文件 50 MB，一次最多 20 个；批量 URL/PDF 会启动后台解析与 LLM 调用）。
- 现状：理论上单次请求可在内存中放入约 1 GB PDF，且没有用户级并发数、队列长度、日配额和全局任务并发上限。
- 影响：少量请求即可耗尽 Node 进程内存、数据库连接或 LLM 额度。
- 修复：改为磁盘/对象存储流式处理；设置请求总大小；把 PDF 上限降到业务需要的合理值；队列采用固定 worker 并发；增加用户级并发、每日数量和费用配额；超额返回 `429`。

### P0-3：认证和验证码接口没有速率限制

- 位置：`artifacts/api-server/src/routes/auth.ts` 的注册、登录、验证码重发/验证、忘记密码与重置密码接口。
- 现状：没有按 IP、账号和设备维度限流，也没有连续失败锁定。
- 影响：可被用于密码喷洒、六位验证码穷举、邮件轰炸和账号枚举辅助攻击。
- 修复：在反向代理和 Express 两层限流；登录采用 IP+邮箱组合键；验证码验证限制次数并在成功/超限后作废；重发设置冷却时间；记录安全审计事件。

### P1-1：管理员角色被固化在 30 天 JWT 中

- 位置：`artifacts/api-server/src/routes/auth.ts` 的 `signToken()`、`requireAdmin()`。
- 现状：JWT 有效期 30 天，鉴权直接信任 token 内的 `role`，不会读取数据库中的最新角色。
- 影响：管理员被降权或账号被禁用后，旧 token 仍可继续执行管理员操作，直到过期。
- 修复：访问 token 缩短到 15–60 分钟并增加 refresh token 轮换；管理员操作从数据库读取当前角色/禁用状态；加入 token version 或会话表以支持强制撤销。

### P1-2：PDF 解析器内置过旧 PDF.js

- 位置：`artifacts/api-server/package.json` 的 `pdf-parse`；安装包默认加载内置 PDF.js `v1.10.100`。
- 现状：该解析器年代久远，包含已知高风险 PDF.js 攻击面；上传内容由普通登录用户提供。
- 影响：恶意 PDF 可能触发解析器漏洞、进程崩溃或资源耗尽。
- 修复：替换为持续维护且使用受支持 PDF.js 版本的解析方案；在独立低权限进程/容器中解析；设置 CPU、内存、页数和超时限制；升级前后用现有 PDF fixtures 回归。

### P1-3：确认入库过度信任客户端提交的数据

- 位置：`artifacts/api-server/src/routes/upload.ts` 的 `/resources/upload/confirm` 与 `/jobs/:id/confirm`。
- 现状：同步确认接口直接接受客户端提供的完整草稿和标签；异步任务确认虽校验 job 所有者，但未强制将提交内容与服务器保存的 job result 做字段级约束。
- 影响：用户可绕过前端，提交不存在/非 active/跨 facet 的标签 ID，或伪造未经过预览阶段的数据；也会增加竞态和脏数据概率。
- 修复：同步预览签发短期一次性确认 ID；服务端保存或签名候选结果；确认时只允许白名单字段覆盖；重新校验标签存在、active 状态与 facet；确认操作使用事务。

### P1-4：关键多表写入缺少事务，存在部分成功

- 位置：注册流程、`persistConfirmedDraft()`、作者同步、标签关联、重复候选写入、密码重置。
- 现状：资源主表、作者关系、标签关系、重复候选分别写入；任一步失败都会留下半成品。密码更新与 token 作废也不是同一事务。
- 影响：数据库可能出现资源存在但作者/标签缺失、密码已更新但 token 仍可复用等不一致状态。
- 修复：把每个业务动作包在单个数据库事务中；依赖外部邮件的流程采用 outbox/补偿机制；为幂等键和唯一约束编写并发测试。

### P1-5：资源所有者可硬删除已审核内容

- 位置：`artifacts/api-server/src/routes/resources.ts` 的 `DELETE /resources/:id`（约 327–342 行）。
- 现状：管理员或创建者均可物理删除，不区分资源是否已 approved。
- 影响：普通用户能删除已经公开、审核过且可能被引用的馆藏记录，破坏审计链和链接稳定性。
- 修复：普通用户只能撤回尚未审核的自有记录；approved 内容只能提交删除申请或由管理员归档；使用软删除并记录操作者、时间和原因。

### P2-1：浏览器 localStorage 保存长期访问 token

- 位置：`artifacts/stablecoin-hub/src/lib/auth-context.tsx`。
- 现状：token 存入 `localStorage`，任何同源 XSS 都可读取；同时服务端未配置 CSP 等安全响应头。
- 修复：优先采用 `HttpOnly + Secure + SameSite` Cookie；补 `helmet`、严格 CSP、HSTS、`frame-ancestors`、`nosniff`；继续审查所有富文本和外链渲染点。

### P2-2：请求体和错误信息边界不完整

- 位置：`artifacts/api-server/src/app.ts`、`routes/upload.ts`。
- 现状：JSON/body parser 没有显式业务上限；若干 500 响应把 `err.message` 作为 `detail` 返回客户端；上传 job 会持久化底层错误文本。
- 影响：大请求消耗内存，底层服务信息可能泄露；错误内容若将来直接渲染还会扩大前端注入面。
- 修复：为 JSON、表单和各上传入口分别设置上限；生产环境只返回稳定错误码和用户可读信息；详细堆栈只写服务端日志并做敏感信息清洗。

### P2-3：CORS 默认退化为允许任意来源

- 位置：`artifacts/api-server/src/app.ts`。
- 现状：`CORS_ORIGIN` 未设置时使用 `origin: true`，会反射任意请求来源。
- 影响：当前 Bearer token 模式下风险低于 Cookie 模式，但会扩大 API 被第三方网页调用的范围；改用 Cookie 后风险会显著提高。
- 修复：生产环境强制要求明确的允许来源列表；开发环境单独允许 localhost；若改用 Cookie，同时配置 credentials、SameSite 与 CSRF 防护。

### P2-4：查询缺少统一分页与返回字段收敛

- 位置：resources、authors、our-research、regulatory 等列表接口。
- 现状：部分接口一次返回全表，公开接口常直接返回整行数据库对象。
- 影响：数据量增长后会拖慢数据库和前端，也容易无意暴露新增内部字段。
- 修复：统一 `limit/cursor` 分页并设置最大值；为公开响应定义显式 DTO；OpenAPI 与运行时 schema 同步校验。

### P2-5：重置 token 与验证码以明文保存

- 位置：`lib/db/src/schema/users.ts`、`artifacts/api-server/src/routes/auth.ts`。
- 现状：密码重置 token 和六位验证码直接入库。
- 影响：数据库只读泄露时，尚未过期的凭证可直接使用。
- 修复：只保存 SHA-256/HMAC 摘要，校验时对输入做同样处理；清理已使用/过期记录；验证码结合失败次数和短有效期。

## 三、本轮已经消除的相关问题

- “我们的研究”新增/删除请求现在携带 Bearer token，且新增和删除按钮只对管理员显示；后端原有 `requireAdmin` 保持为最终权限边界。
- 监管新增/修改/删除接口使用 `requireAuth + requireAdmin`；公开用户只有读取权限。
- 新增监管记录创建者外键和监管—资源关联表，为后续审计与关系管理保留数据基础。

## 八、补充修复与复核（2026-08-25）

### 本轮关闭或显著收敛的风险

- 确认接口会重新执行公网 URL/SSRF 校验，不再信任预览阶段之后被客户端替换的 URL。
- 上传标签使用服务端短期一次性 preview ID；只能确认预览返回且仍为 active 的标签。
- 资源、作者关系、标签关系、重复候选和任务领取已合并进事务；同一 DOI/URL/标准化题名使用 advisory lock 防止并发重复入库。
- PDF 失败任务保留受管临时文件用于重试；成功或删除任务后清理，并定时删除无任务引用的孤立临时文件。
- PDF 的对外说明和服务端限制统一为 50MB；文件类型、数量、任务配额和请求速率均由服务端执行。
- 生产依赖通过 npm 官方安全接口复核：`pnpm audit --prod` 未发现已知漏洞。
- 空闲上传队列不再每 3 秒持续请求，降低 Render/API/Supabase 的无意义负载。

### 仍需在公开部署前完成

1. PDF/OCR 仍在 API 进程内执行；应迁移到独立低权限 worker，并增加页数、CPU、内存和总时长硬限制。
2. 登录仍使用 localStorage Bearer token；应迁移到 HttpOnly Cookie + refresh/session 撤销 + CSRF 防护。
3. 当前任务调度和一次性 preview 的部分状态仍是单实例内存结构；Render 扩为多实例前迁移到数据库或 Redis。
4. 公共列表仍需统一 cursor 分页与显式 DTO，减少数据量增长后的性能和字段泄漏风险。
5. 两条 2026-07-01 的历史种子资源没有提交人和原始审核时间。现有证据不足，不应伪造审核人或时间；迁移档案时需明确标记为 legacy seed。
