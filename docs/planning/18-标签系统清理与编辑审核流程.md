# Claude Code 实现说明(18号)── 标签系统清理 / 关键词前台化 / 用户编辑审核流程

> 起因:修改 Crypto Wash Trading 一条记录的关键词时,发现资源编辑页同时存在两套标签系统(旧的 Research Tags/Additional Tag,和真正符合规范但被锁在 admin 下的 Theme/Jurisdiction/Asset facet)。借此机会一并定下标签/关键词的编辑权限模型。
> 原则同前:小颗粒 commit、每个 commit 跑通 typecheck 再下一个。

---

## 背景说明

### 问题 1 —— 两套标签系统并存,前端展示与文档规范(T.1–T.5)不符
资源编辑页目前有:
- **Research Tags(最多选3个)**:一套约12个粗颗粒选项(Regulation & Policy、CBDC、Systemic Risk 等),不属于 T.2 定义的主题标签词表
- **Additional Tag(最多1个)**:补充标签字段,同样不在 T.1–T.5 规划范围内
- **Facet Tags (admin) → Theme / Jurisdiction / Asset**:这才是真正按 T.2/T.3 落地的受控词表,但目前只有管理员能看到/编辑

跟原定"摘要 → 关键词 → 标签"单一标签区、公开展示、可点击聚合(T.5)的设计不符,是实现走偏,需要清理。

### 问题 2 —— Theme 标签词表数量(已解决,见17号文档)
Theme 标签实际数量与 T.2 文档记录的数字曾一度对不上,已确认是17号文档《理论背景标签与相关性修正》新增的4个标签(shadow-banking、money-market-funds 归入类型与机制类目;crypto-asset-foundations、blockchain-foundations 归入技术与基础设施类目),已实现(commit 988bb14)。这部分不需要本文档处理。

### 问题 3 —— 标签/关键词编辑权限模型(本次确定)
最终方案:**任何登录用户都可以编辑资源的标签(从受控词表选)和关键词(3–5个自由文本)**。
- 普通用户提交的编辑 → 进入审核队列,不立即生效,管理员批准后才应用到公开展示
- 管理员提交的编辑 → 直接生效,无需审核
- 管理员编辑不会自动触发 U.4 的核对 agent 重新核验(沿用既有策略),但资源的 `status` 字段该按正常规则更新还是会更新——这是两件不同的事,不要混为一谈(见 Commit 18.4)

**范围说明**:本次审核流程仅针对**标签和关键词**这两个字段。标题/摘要/作者/DOI等其它字段的编辑权限维持现状(仍是上传者本人+管理员),不在本次改动范围内,后续如需要可再扩展这个模式。

### 问题 4 —— 管理员专属 UI 提示的角色隔离 + 措辞错误
"Admin edits don't trigger re-verification — status is left unchanged" 这条提示目前普通用户也能看到,且措辞不准确:管理员编辑不会自动重新核验是对的,但"status 不会变"是错的——比如补充遗漏的 DOI 后,status 会按正常完整性规则从 needs_review 变为 approved/pending。这是"跳过核对 agent"和"状态判定逻辑"两件事,提示文案却把二者混在了一起。

## Commit 18.1 —— 修正角色化 UI 文案(快速修复,优先做)
- "Admin edits don't trigger re-verification" 类提示只在管理员账号下的编辑页面渲染,普通用户账号下不出现该 DOM/组件(不是靠 CSS 隐藏,是根据角色决定是否渲染)
- 文案改为准确表述,例如:"管理员编辑不会自动触发核对 agent 重新核验;资源状态仍会按常规完整性规则更新。如需重新核验请使用「重新核验」按钮手动触发。"
- 建立通用规范(写入团队开发约定,不止这一条):新增任何面向角色的提示文案/按钮/字段时,设计阶段就要标注"仅管理员可见"还是"所有用户可见",而不是实现完再补丁区分
- 验收:普通用户账号下编辑资源,看不到任何管理员专属提示;管理员账号下文案准确、不再有"status 不会变"这类会被具体案例证伪的说法

## Commit 18.2 —— 下线旧标签系统(Research Tags + Additional Tag)
排查发现,旧标签系统的逻辑几乎完全嵌在 `/resources/import` 系列的4个旧路由里,这几个路由已被 upload.ts 的新管线取代,目前无调用方,是死代码。**但"几乎完全"不等于"完全"**,不能因为路由是死的就默认旧标签系统已经清干净,按依赖顺序分四步处理:

a) **确认死代码范围**(先做,风险最低,可独立提交):
   - grep 全仓确认这4个路由有没有被路由注册表(router/index 或等价文件)挂载;若挂载了但没人调用,连挂载代码一并摘除,不要只删 handler 文件留一个指不到任何代码的挂载点
   - 确认没有测试文件(单测/e2e)还在调用这4个路由——"测试还在跑"是死代码判断最常见的漏网点
   - 确认没有其它文件(迁移脚本、种子脚本、共享常量文件)import 了这4个路由里定义的东西(比如 Research Tags 的选项列表,即使路由本身不可达,里面定义的常量仍可能被别处复用)
   - 确认无误后删除这4个路由文件

b) **确认真正的写入路径**:前端资源编辑页现在提交 Research Tags/Additional Tag 的修改,实际调用的是哪个接口?如果不是刚删掉的4个死路由,说明还存在一条没被发现的活的写入路径,需要一并找到并处理

c) **前端清理**:移除资源编辑页 Research Tags / Additional Tag 两个字段的展示/编辑 UI

d) **历史数据迁移**:检查这两套字段对应的数据库列/表是否有历史数据。有则先做一次性迁移——能语义映射到 Theme/Jurisdiction/Asset 受控词表的,映射后写入 `resource_tags`;映射不进的按 T.4 走候选队列;无法自动判断的记录进迁移日志交人工复核,不直接丢弃。**数据迁移确认无误后,再删除旧字段/表结构本身**——不要在数据没迁移前就删表,否则数据丢失且不可逆

- 验收:全仓搜不到这4个死路由的引用;资源编辑页只剩 Theme/Jurisdiction/Asset 一套标签区;历史数据要么已映射进新词表/候选队列,要么在迁移日志里可查;旧字段/表结构在数据迁移确认完成后才删除

## Commit 18.3 —— Facet 标签前台公开 + 统一展示层级
- 详情页/卡片去掉 "(admin)" 标注,Theme/Jurisdiction/Asset 三组标签对所有用户(含未登录访客,如果资源已 approved)可见
- 页面层级按最初规范:摘要 → 关键词 → 标签(按 facet 分组展示)
- 标签保留 T.5 规定的点击聚合能力(点标签 → 列出该标签下全部资源),这个能力也向所有用户开放,不限管理员
- 验收:非管理员用户打开任意已 approved 资源详情页,能看到完整标签区且可点击聚合

## Commit 18.4 —— 标签/关键词编辑权限模型 + 审核队列
- **权限逻辑**:任何登录用户可以编辑资源的 Theme/Jurisdiction/Asset 标签(从受控词表多选,不能自由创建新标签)和关键词(3–5个自由文本,遵循 Commit 16.3(16号文档)已定的规范)
- 新增 `tag_keyword_edit_suggestions` 表:
  ```
  id, resourceId, submittedBy(userId), submittedAt,
  proposedThemeTags(jsonb), proposedJurisdictionTags(jsonb), proposedAssetTags(jsonb),
  proposedKeywords(jsonb),
  status(pending|approved|rejected),
  reviewedBy, reviewedAt, reviewNote
  ```
- **非管理员提交**:写入该表,status=pending;资源当前公开展示的标签/关键词保持不变;提交者本人在该资源详情页能看到"你的编辑待审核"的状态提示(仅提交者自己可见,其他普通用户看不到别人的待审提议)
- **管理员提交**:不经过这张表,直接写入 `resource_tags`/关键词字段,立即生效;不触发核对 agent 重新核验(沿用已定策略);但资源 `status` 字段仍按常规完整性规则正常判定更新(这一点前端/后端逻辑要和"跳过核对 agent"分开写,不要用同一个 if 分支处理)
- 后台新增审核队列页面(可参考现有 needs_review 队列的交互模式):列出所有 pending 的标签/关键词修改,展示 diff(当前值 vs 提议值),管理员可逐条批准或驳回;批准后立即生效并写入 `resource_tags`,驳回则该条记录标记 rejected(可选填驳回原因),不影响资源当前展示内容
- 验收:普通用户提交的标签/关键词修改不会立刻改变资源公开展示内容;管理员在审核队列里能看到 diff 并批准/驳回;管理员自己发起的编辑不经过队列直接生效
