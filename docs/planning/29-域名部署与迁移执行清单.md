# 29｜域名、部署与网站迁移执行清单

> 更新日期：2026-09-11  
> 当前生产前端：`https://stablecoins-hub.onrender.com`  
> 当前生产 API：`https://stablecoins-research-hub.onrender.com`  
> 目标：在不修改业务代码、不调整 PDF 上传大小等产品配置的前提下，先完成可供老师浏览的演示入口；之后再决定是否从 Render 迁移到 Linode。  
> 硬性验收：国内和国外的普通网络均可直接访问，不依赖 VPN。这里的“可访问”必须通过多网络实测确认，不能仅凭机房地理位置推断。

## 一、先定结论

### 1.1 推荐路线

- [ ] **优先向 ZIBS/浙大申请机构子域名**，例如 `stablecoin.zibs.zju.edu.cn`；学校没有可用计算服务器，不妨碍学校把域名解析到 Render 或 Linode。
- [ ] 如果机构子域名暂时不能批，**购买 `.com` 作为独立主域名**。
- [ ] `.ai` 仅在老师明确希望突出 AI 品牌、并接受较高续费成本时购买；本项目主体是稳定币研究平台，`.com` 的含义更中性，也更省预算。
- [ ] **演示阶段先不迁服务器**：把新域名绑定到现有 Render 前端和 API，保留两个 `onrender.com` 地址作为回退入口。
- [ ] 演示前冻结一个可用版本，仅浏览公开页面，不进行上传、批量导入、管理员审核或数据库迁移。
- [ ] 演示通过后，再用短期测试实例比较 Linode 新加坡、东京/大阪等候选区；实测合格才迁移。
- [ ] Linode 初期采用 `Nanode 1 GB / 1 shared vCPU / 25 GB / 1 TB transfer / US$5 每月`。它适合低流量演示和轻量网站，不把它视为 PDF/OCR、批量 AI 处理同时开放时的长期生产规格。
- [ ] 迁移 Linode 时只迁应用运行环境，**数据库继续使用现有 Supabase/PostgreSQL**，先不做数据库搬家。

### 1.2 为什么不直接迁 Linode

域名切换和服务器迁移是两件事。先把自有域名接到 Render，可以用最小变更获得正式演示网址；若同时换域名、服务器、反向代理和 TLS，出问题时很难判断故障来自哪一层。

当前 Render 还承担自动构建、静态站点、Node API、TLS 和回滚。Linode 是裸云主机，改用它后，系统更新、防火墙、Node 进程、反向代理、证书续期、日志和备份都要自行维护。

## 二、域名选择与“二级域名”说明

### 2.1 三种选择

| 选择 | 示例（仅示意，不代表已获批或可注册） | 费用 | 优点 | 限制 | 建议 |
| --- | --- | ---: | --- | --- | --- |
| ZIBS/浙大机构子域名 | `stablecoin.zibs.zju.edu.cn` | 通常无需另购域名 | 学术身份最清晰、可信度最高 | 需要学校网信/信息化部门授权和 DNS 配合 | 第一优先 |
| 独立 `.com` | `项目名.com` | 当前常见首年约 US$11–15，续费约 US$18/年；以结算页为准 | 国际通用、便宜、含义中性 | 好名字可能已被注册 | 第二优先、独立域名推荐 |
| 独立 `.ai` | `项目名.ai` | 当前通常要求至少注册 2 年；示例报价约 US$180/2 年，续费约 US$230/2 年 | 技术感强 | 明显更贵，且容易让访问者以为平台核心是 AI | 仅在品牌需要时选 |

价格快照只用于预算，记录于 2026-09-11；购买前必须再次核对“首购价、正常续费价、最低年限、隐私保护、税费、赎回费”，不能只看促销价。

### 2.2 “二级域名”到底是什么

- 严格 DNS 术语中，`example.com` 的 `example` 是 `.com` 下的二级域；`www.example.com` 和 `api.example.com` 是它的子域（从完整层级看是三级域名）。
- 国内日常表达常把 `www.example.com`、`api.example.com` 也称为“二级域名”。本清单后文统一称为**子域名**，避免歧义。
- 子域名不需要再次购买。只要拥有主域名或获得学校 DNS 管理员授权，就可以添加多个 DNS 记录。

### 2.3 推荐命名结构

演示阶段在 Render 上：

| 入口 | 推荐地址 | 用途 |
| --- | --- | --- |
| 主站 | `https://www.<主域名>` 或 `https://<主域名>` | React/Vite 前端；二选一作为唯一规范地址 |
| API | `https://api.<主域名>` | Express API |
| 旧前端 | `https://stablecoins-hub.onrender.com` | 临时回退，不立即关闭 |
| 旧 API | `https://stablecoins-research-hub.onrender.com` | 临时回退及浏览器插件兼容，不立即关闭 |

迁到单台 Linode 后，推荐由同一个域名提供网页和 `/api/*`，由 Nginx 把 `/api/*` 反向代理到本机 Node 服务。这样可以减少跨域配置和 DNS 故障点；`api.<主域名>` 可保留为兼容入口。

- [ ] 后端 Web Service 添加 `api.<主域名>`。
- [ ] 记录 Render 对每个域名给出的 A/CNAME/验证记录。

只调整部署环境变量，不改代码：

- [ ] 前端 `VITE_API_BASE_URL=https://api.<主域名>`，然后触发一次前端重新构建。

- [ ] 先发布 API，再发布前端。

**A2 完成标准：** 新域名 HTTPS 正常，旧 Render 地址仍可回退，页面请求不出现 CORS 或 mixed-content 错误。

- [ ] 如果演示不测试注册/忘记密码，本项可推迟，不阻塞公开页面浏览。

### A4｜国内外“不用 VPN”验收

必须测试完整网页和 API，单独 `ping` 通不能代表网站可用。每个网络在上午、下午、晚间各测至少 3 次，记录中位数和失败次数。

- [ ] 中国移动手机网络：打开首页、市场数据、监管页面和一条资源详情。
- [ ] 中国联通手机网络：执行同样路径。
- [ ] 中国电信或校园网：执行同样路径。
- [ ] 一个境外网络：执行同样路径。
- [ ] 每次同时检查 `https://api.<主域名>/api/healthz` 返回 `200` 和 `{"status":"ok"}`。
- [ ] 浏览器开发者工具确认：DNS/TLS 成功、无证书警告、无 CORS、关键 JS/CSS/字体无大面积失败。
- [ ] 记录 DNS 时间、TTFB、首屏完成时间和是否出现 Render 冷启动。
- [ ] 验收线：各网络连续测试无连接失败；暖机后 API 健康检查建议小于 2 秒、首屏建议 5 秒内可用。若未达标，记录事实后进入阶段 B，不宣称“已保证国内可访问”。

可重复使用的只读检查命令：

```bash
dig +short <主域名>
dig +short api.<主域名>
curl -I --max-time 15 https://<主域名>
curl --fail --show-error --max-time 15 https://api.<主域名>/api/healthz
```

## 五、阶段 B：Linode 区域试验与迁移决策

### B1｜先测试机房，不先承诺机房

Akamai/Linode 官方建议亚太广域业务考虑新加坡或悉尼，并强调网络结果要多次测试。针对本项目国内外访问目标，候选顺序建议为新加坡、东京、大阪；最终顺序以三大运营商实测为准。

- [ ] 在候选区使用按小时计费的 1 GB 实例做短期测试，测试完停止计费资源。
- [ ] 每个候选区部署同一个最小 HTTPS 页面和健康检查，避免测试内容不同。
- [ ] 从中国移动、联通、电信/校园网和一个境外网络重复 A4 的测试。
- [ ] 记录路由稳定性、晚高峰丢包、TLS、TTFB、下载 1 MB 静态文件和 API 响应。
- [ ] 选“成功率与晚高峰稳定性最好”的区，不只选平均延迟最低的区。
- [ ] 如果所有境外区在大陆网络都间歇失败，则 Linode 方案不满足硬性要求，停止迁移。

### B2｜有关 ICP 和中国大陆加速的边界

- 工信部规则要求在中国境内提供非经营性互联网信息服务依法备案。把服务器放在境外，通常不能直接使用中国大陆节点/CDN来获得备案型本地加速。
- 普通 Cloudflare 全球免费网络不等于 Cloudflare China Network。Cloudflare 当前说明 China Network 是 Enterprise 的单独订阅，并要求每个主域名具有有效 ICP 备案/许可证。
- 境外 Render 或 Linode 可以在很多情况下被国内普通网络直接访问，但跨境链路存在延迟和可靠性波动，不能提供“全国三网永久可达”的保证。

若境外节点无法通过验收：

- [ ] 与学校确认能否用学校主体完成 ICP 备案和内容合规审核。
- [ ] 评估阿里云/腾讯云等境内实例或学校认可的境内托管；稳定币内容上线前由学校网信/法务确认边界。
- [ ] 若仍保留境外源站，另行询价合规的中国加速产品，不把 Cloudflare 免费代理当作解决方案。

**B 阶段决策门：** 只有候选区通过 A4 同等级别测试，才采购长期实例并进入 C 阶段。

## 六、阶段 C：迁移到 Linode 1 GB

### C0｜适用范围

1 GB 方案只按“低并发、以浏览为主、数据库在 Supabase、AI 通过外部 API”的演示/轻量站点设计。当前 API 仍在同一进程处理 PDF/OCR 和后台任务；若开放多人上传、批量 OCR 或并发 AI 任务，应先升级至至少 2 GB，或把 worker/队列独立出去。

### C1｜创建和加固主机

- [ ] 创建测试胜出的区域、Ubuntu LTS、Nanode 1 GB 实例。
- [ ] 只使用 SSH key；创建非 root 运维用户并授予必要的 `sudo`。
- [ ] 禁用 SSH 密码登录和 root 远程登录。
- [ ] 配置 Linode Cloud Firewall：公网只开放 TCP 80/443；22 仅允许管理员固定 IP，若无固定 IP则制定临时放行流程。
- [ ] 安装安全更新并启用自动安全补丁。
- [ ] 创建 1–2 GB swap，降低安装依赖或短时峰值导致 OOM 的概率；swap 不是扩容 RAM 的替代品。
- [ ] 设置服务器时区、NTP、主机名和日志轮转。
- [ ] 开启 Linode 备份或制定等价快照计划；确认其额外价格后写入预算。

### C2｜部署结构

推荐单机结构：

```text
浏览器
  └─ HTTPS :443 / Nginx
       ├─ /、静态资源 → artifacts/stablecoin-hub/dist/public
       └─ /api/*       → 127.0.0.1:3000 / Node API
                              └─ Supabase PostgreSQL（暂不迁移）
```

- [ ] 使用 Node.js 24 与 pnpm 11.9.0，和仓库声明保持一致。
- [ ] 不在 1 GB 生产机上长期保留完整开发依赖。优先在本地或 CI 完成 `pnpm run typecheck`、`pnpm run build`，再发布经过校验的产物。
- [ ] 在一次完整预演中确认 API 构建产物所需运行时依赖；当前 `build.mjs` 将 `nodemailer` 等列为 external，不能未经测试就只复制单个 `index.mjs`。
- [ ] 每次发布使用独立 release 目录和 `current` 软链接，至少保留上一个可启动版本用于回滚。
- [ ] 用 systemd 管理 Node API，设置自动重启、启动超时和内存观察；Node 只监听 `127.0.0.1:3000` 或由防火墙确保 3000 不对公网开放。
- [ ] 用 Nginx 托管前端、处理 SPA fallback，并反向代理 `/api/*`。
- [ ] Nginx 请求体上限保持与应用现有 PDF 50 MB 限制一致，避免默认网关上限把现有功能意外改小；这只是保持现状，不提高应用限制。
- [ ] 使用 Let's Encrypt/Certbot 自动签发与续期 HTTPS，并执行一次模拟续期检查。
- [ ] 为 `/api/healthz` 配置外部监控；监控只告警，不用高频访问规避平台规则。

### C3｜环境变量迁移

- [ ] 从 Render 控制台逐项核对变量名，不在终端历史、Git、Markdown 或聊天中输出真实值。
- [ ] 将生产变量放到 root 可读、权限 `0600` 的独立环境文件，由 systemd `EnvironmentFile` 引用。
- [ ] 必需项核对：`NODE_ENV`、`PORT`、`DATABASE_URL`、`JWT_SECRET`、`LLM_API_KEY`、`EMAIL_PROVIDER`、`FRONTEND_URL`、`CORS_ORIGIN`、`SCHOLAR_CONTACT_EMAIL`。
- [ ] 按邮件提供商核对 Brevo 或 Microsoft Graph 的条件变量。
- [ ] 前后端同源时，前端 `VITE_API_BASE_URL` 留空/不设置并在预演中确认 `/api` 同源请求；后端 `FRONTEND_URL` 与 `CORS_ORIGIN` 使用规范主域名。
- [ ] 切换期先保持原 `JWT_SECRET`，避免所有现有会话立即失效；稳定后若轮换密钥，要把“用户需重新登录”写进变更通知。

### C4｜数据与状态清点

| 对象 | 当前位置 | 本轮是否迁移 | 操作 |
| --- | --- | --- | --- |
| 代码 | GitHub `main` | 是 | 固定提交/标签部署 |
| 前端构建产物 | Render Static Site | 是 | 构建后放到 Nginx 静态目录 |
| API | Render Web Service | 是 | systemd 启动 Node bundle 与运行时依赖 |
| 业务数据库 | Supabase PostgreSQL | 否 | 迁移前备份，Linode 继续连原库 |
| PDF 临时文件 | Render 临时磁盘/进程任务 | 否 | 切换前清空任务；成功任务不依赖持久本地 PDF |
| 进程内队列/一次性确认状态 | Render API 内存 | 不可直接迁 | 切换前排空；不要在有活跃任务时重启 |
| Render 日志 | Render | 否 | 导出必要的部署/故障记录，旧服务保留期内可查 |
| 浏览器插件地址 | 仓库中写死 Render URL | 暂不改 | 网站演示不使用插件；后续单独改配置、权限并重打包 |

### C5｜Linode 上线前验收

- [ ] 使用临时子域名（如 `preview.<主域名>`）完成全站检查，不先改正式 DNS。
- [ ] `systemctl` 显示 API 持续运行，重启主机后能自动恢复。
- [ ] `/api/healthz`、公开资源列表、作者、监管、市场数据页均返回正常。
- [ ] 登录只做一次最低限度验证；不在演示期做批量上传/OCR 压测。
- [ ] 查看空闲和浏览高峰的 RAM、swap、CPU、磁盘和数据库连接数。
- [ ] 用 A4 的四类网络再测至少一天，包括晚高峰。
- [ ] 检查 TLS、HSTS、安全响应头、CORS 和 Nginx 上传上限未意外改变。
- [ ] 记录 release 路径、systemd 服务名、Nginx 配置路径、证书续期方式和回滚命令。

## 七、阶段 D：零停机 DNS 切换与回滚

### D1｜切换前 24–48 小时

- [ ] 把正式域名 TTL 降到 300 秒。
- [ ] 再次备份 Supabase；确认本轮没有数据库 migration。
- [ ] 排空上传/审核/后台任务，冻结发布。
- [ ] 对比 Render 与 Linode 的关键页面和 API 响应。
- [ ] 保持 Render 服务、环境变量和 `onrender.com` 地址不变。

### D2｜切换顺序

- [ ] 先将 `api.<主域名>` 或同源 `/api` 入口指向 Linode，并检查健康状态。
- [ ] 再将规范主域名指向 Linode 公网 IP。
- [ ] 等待 DNS 生效，分别从国内三网和境外网络验证。
- [ ] 检查邮件中的链接、登录 token、CORS 和浏览器缓存。
- [ ] 连续观察 24–72 小时的 5xx、进程重启、内存、磁盘、数据库连接和外部 API 错误。
- [ ] 稳定一周后再提高 TTL；Render 至少保留 7 天作为回退，不立即删除。

### D3｜回滚触发条件

满足任意一项即回滚：

- 国内任一主要运营商持续无法解析或建立 HTTPS；
- API 连续出现无法自动恢复的 5xx；
- 1 GB 实例 OOM/频繁 swap，影响普通浏览；
- Supabase 连接不稳定或数据写入出现异常；
- TLS、CORS、登录/邮件链接出现无法在短时间修复的问题。

回滚步骤：

- [ ] DNS 恢复指向 Render 给出的记录。
- [ ] 前端 `VITE_API_BASE_URL` 恢复 Render API 或保留仍可用的自定义 API 域名。
- [ ] 后端 `FRONTEND_URL`、`CORS_ORIGIN` 恢复到仍在使用的前端来源。
- [ ] 验证原 `/api/healthz`、首页和公开数据。
- [ ] 保留 Linode 实例和日志用于排查，不在故障当下删除资源。

## 十、已识别的仓库特定风险

- [ ] 仓库当前没有 `render.yaml`，Render 的关键设置主要存在控制台；迁移前必须把“变量名、构建命令、发布目录、SPA rewrite、健康检查路径”记录齐全，但不记录秘密值。
- [ ] 浏览器插件的 `artifacts/browser-extension/src/config.js` 与 `manifest.json` 写死两个 Render 地址。演示网页时可继续保留；若老师要演示插件，必须另开任务修改域名、host permissions、版本号并重新打包。
- [ ] 多处前端通过 `VITE_API_BASE_URL` 找 API；换 API 域名必须触发前端重建，仅改 DNS 不够。
- [ ] 后端生产 CORS 只允许 `CORS_ORIGIN` 中列出的来源；新域名漏配会导致页面打开但数据请求失败。
- [ ] `FRONTEND_URL` 用于邮件链接；漏改会让密码重置跳回旧域名。
- [ ] Render 免费 API 空闲后会冷启动，演示前应主动打开，不用定时器规避休眠规则。
- [ ] API 当前包含进程内队列和 PDF/OCR 工作；1 GB 主机只适合浏览为主的初期阶段。
- [ ] 当前安全审计仍把 HttpOnly Cookie、分布式限流/队列、独立 PDF worker 等列为正式大规模开放前的后续项；换服务器不会自动解决这些问题。

## 十一、完成定义

本任务只有同时满足以下条件才可标为完成：

- [ ] 域名归属、续费、DNS 权限和交接人有记录。
- [ ] 新域名 HTTPS 正常，网页与 API 均使用预期地址。
- [ ] 国内移动、联通、电信/校园网和一个境外网络均通过无 VPN 实测。
- [ ] 演示版本冻结且可回滚，Supabase 有已验证备份。
- [ ] 没有修改业务代码、数据库 schema 或 PDF 上传限制。
- [ ] Render 旧地址在观察期内仍可用。
- [ ] 若已迁 Linode，systemd、Nginx、TLS、监控、备份和回滚均经过实际演练。
- [ ] 若只完成演示阶段，则明确标记“阶段 A 完成，Linode 尚未迁移”，不要把计划项写成已完成。
