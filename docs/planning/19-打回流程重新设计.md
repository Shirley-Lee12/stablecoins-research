# Claude Code 实现说明(19号)── 打回流程重新设计:防止死循环 / 理由具体化 / 重复资源处理

> 起因:排查发现已有的重新提交流程(见更早文档的0.7)存在一个真实缺陷——重新提交后系统会用同一套自动检测重跑一遍`off_topic`/`disputed`/`duplicate`判断,如果用户认为判断有误但内容没有实质变化,会陷入死循环,永远到不了`pending`。借此机会一并把打回理由具体化,并把重复资源的处理流程钉清楚。
> 原则同前:小颗粒 commit、每个 commit 跑通 typecheck 再下一个。

---

## 背景说明

现有状态机(七状态最终版):`incomplete`(待补充)/`disputed`(待核实)/`off_topic`(与稳定币无关)/`duplicate`(疑似重复)/`pending`/`approved`/`rejected`。前四种是系统自动打回、仅用户自己可见。

原设计(0.7)里,用户修改后重新提交,系统"重新跑一次完整检查(完整性+核对agent+主题相关性+重复检测),全部通过才真正进入pending"。问题在于:`off_topic`/`disputed`/`duplicate`都是**自动检测出来的信号**,如果用户不认同判断、也没有实质性修改内容,重新提交时同一套自动检测大概率还会得出同样的结论,导致用户永远卡在打回状态,进不了管理员审核。

---

## Commit 19.1 —— 修正重新提交检查逻辑,打破死循环(覆盖0.7旧规则)
- **旧规则作废**:重新提交后跑全套检查(完整性+核对agent+主题相关性+重复检测)
- **新规则**:重新提交后,**只重新检查完整性**(六要素:标题/作者/年份/摘要/关键词/URL·DOI 是否齐全)。完整性通过 → 直接进入`pending`,交给管理员做最终判断;完整性仍不通过 → 继续留在`incomplete`,展示还缺哪些
- 不再重新跑核对agent(disputed的判断依据)、主题相关性(off_topic)、重复检测(duplicate)——这三类一旦触发过一次自动打回,用户的下一步动作就是"修改或说明后重新提交",系统对此不再二次自动拦截,而是把判断权交给管理员(管理员在审核时能看到原始打回原因+用户的修改/说明,见19.2)
- 这个改动只影响"重新提交"路径,**首次提交仍然要跑全套检查**来决定是否需要打回
- 验收:一条被判`off_topic`的资源,用户不修改任何与主题相关的内容、只补一句说明后重新提交,应该正常进入`pending`,不会被系统再次判`off_topic`打回

## Commit 19.2 —— 打回理由具体化展示(四类状态都要,不只是状态标签)
现状:用户在 My Contributions 只看到一个状态标签(比如"与稳定币无关"),不知道具体原因,不好判断该怎么改。

- `incomplete`:列出具体缺了哪几项字段(沿用已有设计)
- `disputed`:复用现有核对报告的✅/⚠️/❌逐字段展示(沿用已有设计)
- `off_topic`:**新增**——需要一段自然语言解释,不能只说"未命中主题标签"。触发`off_topic`时,用摘要/标题做一次轻量LLM调用,生成类似"这篇资源研究的是XX,没有直接以稳定币为研究对象,也没有涉及稳定币相关的理论和技术基石"这种具体表述。**生成后存下来,不用每次展示都重新调用**(跟16号文档"核对报告要落库、不要每次现算"是同一个道理,避免重复消耗 API)
- `duplicate`:展示具体命中的候选重复资源(见19.3),而不只是"疑似重复"四个字
- 验收:打开任意一条打回状态的资源,用户不用猜就能看懂"具体要改什么/为什么"

## Commit 19.3 —— 重复资源处理:显式操作 + 候选列表UI
- 新增 `duplicate_candidates` 表:`id, resourceId, candidateResourceId, matchType(exact_doi|exact_url|fuzzy_title), createdAt`,触发`duplicate`判定时把命中的候选资源都记下来(可能不止一条)
- My Contributions 里 `duplicate` 状态条目:复用现有资源列表卡片样式,展示候选重复资源的基础信息(标题/作者/年份),点击标题打开18.3已经公开的 `ResourceDetailModal` 查看详情,方便用户直接比对
- 用户两个显式操作:
  - **确认是重复** → 新增"撤回"操作,标记为用户主动撤回,不物理删除、保留记录(状态新增 `withdrawn`,对管理员和公开界面都不可见,只在用户自己的 My Contributions 历史里留痕)。**这会让状态机从此前"最终版七状态"变成八个,是本次讨论后新增的,不是当初遗漏**
  - **确认不是重复** → 提供一个简短说明输入框(如"这是同一研究的工作论文版本,与已发表版本不同"),连同原内容一起重新提交;走19.1的新规则(只查完整性),完整则直接进管理员队列,管理员能同时看到用户的说明和原始候选重复资源,做最终判断
- 验收:确认重复能正常撤回,不再出现在任何队列;确认非重复+填写说明后能进入`pending`,管理员审核界面能同时看到用户说明和候选重复资源对比

## Commit 19.4 —— 标签维持现状(确认项,无需改动)
- 本次讨论确认:标签(theme facet)不并入`incomplete`的六要素必填清单,继续单独用`off_topic`处理——标签是AI生成+受控词表,不该由用户"补全"
- 不需要代码改动,写入文档只是为了留痕,避免以后被重新提起来议一遍

## Commit 19.5 —— `failed` 状态清理确认
- 已确认设计层面`failed`不在状态机的七个(现为八个)状态里,需要 Code 核实代码里(schema枚举、状态判定函数、前端状态展示/筛选逻辑)有没有残留引用
- 参照18.2处理死路由的方式:先 grep 确认范围,再删除,不要假设文档说没有就等于代码也没有

## 附:今天 Code 在做 18.4 时提出的现场问题,维持原答案

Code 问:管理员 PATCH 已 approved 资源、编辑字段与遗留缺口无关时,要不要重算 status(会导致现有2条有缺口的 approved 资源被打回 incomplete)。

**维持建议:选"按字面实现"——任何管理员 PATCH 都无条件重算 status**,不做"只在相关字段变化时才重算"的特殊化处理。理由不变(不引入新的字段判断逻辑、和 owner 重新提交路径行为一致),且19.1的新规则进一步支持这个选择——owner 重新提交时也是"无条件重跑完整性检查",不判断"这次改的是不是跟缺口相关的字段"。两条路径用同一个简单原则,比其中一条搞特殊化更不容易出 bug。

补充执行:
- 管理员 PATCH 导致 status 变化时,响应要明确带上"变化前后状态 + 触发原因",前端给管理员可见提示,不能静默发生
- 建议现在就把那2条有缺口的 approved 资源内容补全,避免它们成为第一批"意外触发"的案例
