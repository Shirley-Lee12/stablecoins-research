# Claude Code 实现说明(16号)── 标签校准 / 关键词字段 / 核对报告持久化

> 起因:审阅 Crypto Wash Trading(NBER w30783)一条实测记录时发现三个问题,记录为规划文档,交给 Claude Code 执行。
> 涉及:U.3 标签映射校准、关键词字段规范(3–5 个)、核对报告持久化(修复重复验证浪费 API 的问题)。
> 原则同前:小颗粒 commit、每个 commit 跑通 typecheck 再下一个。

---

## 背景说明

### 问题 1 —— 标签误打:字面相似但语义不同的词被 embedding 匹配带偏
案例:NBER Working Paper *Crypto Wash Trading*(w30783)研究交易所层面"洗售交易"(虚构交易量做市场操纵)的检测方法,与稳定币锚定机制无关。系统自动打标结果:

| 系统打标 | 是否应打 | 问题 |
|---|---|---|
| 锚定与脱锚 | 不应打 | 全文唯一相关文字是脚注提到 USDT "designed to be pegged to USD",用于解释为何把 USDT 交易对等同 USD 处理,属背景带过,非论文主题 |
| 反洗钱 / AML | 不应打 | 论文讨论的是 wash trading(洗售交易/虚假交易量),与 money laundering(洗钱)是完全不同的概念,大概率是 "wash" 一词在向量相似度匹配时把两者关联到了一起 |
| 市场数据与供给 | 保留(勉强) | 论文确实大量讨论"报告交易量"数据质量与 CoinMarketCap 排名机制,但不算精准命中 |
| 交易与市场结构 | 保留(准确) | 论文核心方向,命中正确 |

四个标签里两个明显误判、一个勉强、一个准确。这类"字面相近、语义不同"的词对(pegged/peg stability、wash trading/money laundering)如果单靠摘要与标签定义句的向量相似度匹配(U.3 设计),很容易被字面相似度带偏,且不易在人工审核前被发现。

### 问题 2 —— 关键词字段生成规范缺失
关键词字段规范为每条资源 **3–5 个**关键词(已确认过的既定规则)。此次该资源导入时未生成关键词,需要用户手动补充,说明生成流程目前没有落实这条约束。

### 问题 3 —— 详情页重复触发核对,浪费 API 调用
已有 Verification Report 的资源,打开详情页后又重新显示"Verifying"。怀疑详情页 GET 请求里直接挂了核对逻辑而非纯读库,导致每次打开详情页都重新调用一次核对 agent,消耗 LLM/scholar API 配额。

## Commit 16.1 —— 核对报告持久化(修复重复验证)
- 核对报告(逐字段核对结果,对应 U.4)应在入库前生成一次并落库,而非每次访问详情页现算
- DB:检查 `resources` / `upload_jobs` 是否已有字段存储核对报告;若无则新增 `verification_reports` 表:`id, resourceId, report(jsonb), verifiedAt`
- 后端:资源详情接口(`GET /api/resources/:id` 或等价路由)改为纯读库,不再触发核对 agent 调用
- 若确需重新核验(如资源被人工编辑后),做成显式 `POST /api/resources/:id/reverify` 接口,前端配一个"重新核验"按钮,点击需二次确认弹窗(遵循既有的"自动导入类操作需明确确认"原则,不因为是"重新"核验就跳过确认)
- 验收:反复打开同一条已核验资源的详情页,网络请求里不再出现新的 LLM/scholar API 调用;报告内容与首次核验保持一致

## Commit 16.2 —— 标签映射:易混淆词对治理
- 问题根源在 U.3(embedding 相似度打标)阶段
- 短期(人工侧,优先做):后台标签审核界面增加"取消关联/误打申诉"操作,管理员可对单条资源的单个标签单独移除,不影响其它资源;这是 T.4 候选队列审核机制的自然延伸
- 中期(算法侧,可延后攒案例后再统一处理):
  - 建一份易混淆词对测试集,至少覆盖本次发现的两组:`wash trading` vs `反洗钱/AML`、`pegged`(背景带过用法)vs `锚定与脱锚`;U.3 逻辑调整后跑一遍回归测试,确认误关联不再出现
  - 评估是否给标签定义句加入"排除性说明"(例如反洗钱标签定义句里明确排除 wash trading 一类术语),辅助匹配时降低误命中
  - 若考虑调整相似度阈值,需用已入库资源做前后对比,避免阈值过紧导致漏打
- 验收:测试集中的易混淆词对不再触发误关联;历史误打标签可通过人工审核界面单独修正,不需要重新走一遍完整核对流程

## Commit 16.3 —— 关键词字段规范(3–5 个)
- LLM 抽取关键词时的 prompt 明确约束数量范围 3–5 个,优先选择代表论文核心方法/主题的词(如 `Benford's Law`、`power-law distribution`),而非泛泛的领域词(如单独一个 `cryptocurrency`)
- 核对报告中增加关键词数量校验项:超出或不足 3–5 区间标记 ⚠️,而非直接判失败(参照 U.5 "不因缺一项整条丢弃"的原则)
- 前端资源详情页关键词字段允许用户手动增删;提交时做 3–5 个的软校验(超出/不足给提示,不强制阻断,用户可能有正当理由要更多或更少)
- 验收:新导入资源关键词数量默认落在 3–5 区间;人工手动编辑超出区间时有提示但不阻断保存

## 建议执行顺序
1. Commit 16.1(核对报告持久化)—— 优先,直接影响 API 成本,且是独立的数据层问题
2. Commit 16.3(关键词字段规范)—— 相对独立,可与 16.1 并行
3. Commit 16.2(标签误判治理)前半部分(人工取消关联功能)—— 尽快上线作为应急手段
4. Commit 16.2 后半部分(算法侧调整)—— 建议攒够更多易混淆案例后再统一处理,避免为单个案例频繁调阈值
